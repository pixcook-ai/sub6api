# Sub6 完整核心双 OAuth：Codex / Excel 原生授权与双向切换

日期：2026-11-22（Asia/Shanghai）。状态：六阶段范围、依赖和公开 API 测试接缝已批准；实施与验收仍在进行。

## Problem Statement

管理员需要在 Sub6 内完成 Codex 和 Excel 两种独立授权、保存与恢复授权、选择新会话提供方，并继续使用同一 API 入口。若这些能力依赖个人电脑上的 toSub2 进程或另一刷新权威，Sub6 无法独立运行，也会在刷新令牌旋转、账号交接和会话切换时产生凭据竞争或身份串用。

## Solution

Sub6 是完整核心：独立完成两种 OAuth 的首次授权、加密持久化、刷新、真实上游 401 恢复、授权管理和双向新会话切换。toSub2 是可选管理客户端，停止或未安装时核心路径仍可用。bps-gateway 保持 BPS 协议 worker 边界，核心管理模式只接收访问令牌（AT），刷新令牌（RT）和刷新权威留在 Sub6。既有普通 Codex 路径继续可用。

## User Stories

1. 作为管理员，我希望在 Sub6 内创建核心授权 profile，以便无需启动 toSub2 即可使用核心功能。
2. 作为管理员，我希望分别授权 Codex 与 Excel，以便每份授权使用对应的官方客户端和回调合同。
3. 作为管理员，我希望看到安全的授权状态、身份和到期信息，以便判断下一步操作。
4. 作为管理员，我希望通过本次官方回调 URL 完成 PKCE 事务，以便首版无需手工提供 OAuth 文件。
5. 作为管理员，我希望取消或重新发起过期授权，以便明确恢复失败的授权流程。
6. 作为管理员，我希望只有授权发起者能够完成或取消该事务，以便另一管理员不能接管本次授权。
7. 作为管理员，我希望重新授权期间保留既有可用授权，以便一次未完成操作不会删除可用凭据。
8. 作为运维人员，我希望授权加密持久化并在重启后恢复，以便核心不依赖个人电脑的进程或 Keychain。
9. 作为运维人员，我希望未配置稳定加密密钥时明确显示不可用原因，以便服务仍可启动且不会明文保存凭据。
10. 作为运维人员，我希望并发刷新由单一权威执行，以便 RT 旋转不会被多个调用者竞争使用。
11. 作为运维人员，我希望先持久化旋转后的 RT，再发布新 AT，以便重启后仍有有效刷新凭据。
12. 作为运维人员，我希望刷新超时且结果未知时暂停并提示处理，以便系统不会盲重试已失效的旧 RT。
13. 作为运维人员，我希望 invalid_grant 明确进入重新授权状态，以便故障可理解并可恢复。
14. 作为管理员，我希望仅真实上游 OAuth 401 触发受控恢复，以便入口 401、403 和 429 不引起登录风暴。
15. 作为管理员，我希望迟到的 401 按真实失败 revision 判断，以便旧请求不会重复刷新新凭据。
16. 作为管理员，我希望显式选择模型、能力和新会话调度意图后再切换，以便不会意外启用账号或选择不支持的目标。
17. 作为管理员，我希望切换前核对主体、工作区、分组和策略，以便提供方变化不会破坏身份或资源隔离。
18. 作为管理员，我希望切换失败时保留原路由，以便当前服务不会因失败的操作发生改变。
19. 作为 API 使用者，我希望切换后保留 base_url 与 API key，以便客户端无需修改接入配置。
20. 作为 API 使用者，我希望旧会话、在途请求和既有资源保持原绑定，以便切换只影响新会话。
21. 作为管理员，我希望两个方向切换都保留两份授权，以便缺少目标授权时可以先授权而不是删除旧授权。
22. 作为管理员，我希望人工停调始终有效，以便授权刷新或切换不会自动恢复我暂停的账号。
23. 作为旧受管模式管理员，我希望通过显式围栏和受保护交接迁移所有权，以便迁移过程中始终只有一个刷新者和发布者。
24. 作为运维人员，我希望 worker 只得到当前身份与 revision 一致的 AT 快照，以便协议翻译层不会获得 RT 或自主刷新权。
25. 作为验收人员，我希望从管理员登录、核心 profile 到同一 Sub6 SDK 入口验证完整路径，以便验收反映实际使用方式。
26. 作为验收人员，我希望分别看到合成验证与真实 OAuth、RT 轮换、文件理解和计费证据，以便局部通过不会被误报为真实交付。

## Implementation Decisions

- Codex 与 Excel 是独立授权，使用各自官方 client_id 与精确回调合同；不得通过修改 client_id 转换 token，不将 Excel 回调强改为 localhost。完全自动回交受官方回调合同门控制。
- 核心授权 API 使用既有管理员认证、RBAC 和成功 envelope；公开 DTO 仅包含安全状态和身份信息，令牌、code、PKCE、cookie、完整回调及内部 actor 状态均不出现在 profile DTO 或日志。
- profile 提供创建、列表、查询、发起、完成、取消和 revision 受控刷新；发起者由认证中间件提供，不接受客户端伪造。
- 核心授权仓储复用既有私有 settings 命名空间、加密器与 CAS，无新增迁移；无稳定加密密钥时能力端点明确 unavailable，既有服务仍可启动。
- profile 状态包括 empty、authorizing、authorized、refreshing、refresh_uncertain 和 reauthorization_required；授权尝试具有独立生命周期。重启后未完成尝试明确过期，已持久化授权保留。
- 跨实例 CAS 先于令牌请求取得刷新权；持久化刷新操作标记以区分可重试前置失败和已经发出、结果未知的请求。RT 旋转先持久化再发布 AT，未知结果闭锁，invalid_grant 要求重新授权。
- 401 恢复必须同时匹配 profile、identity epoch、真实失败 token revision、来源 upstream_oauth 和状态 401。保持人工停调，不自动跨 provider，也不自动重放有副作用或已经输出的请求。
- 核心 runtime binding 使用独立所有权合同，拒绝外部 managed marker、含 RT 的运行账号、身份/版本/到期格式错误和 provider/platform 不匹配；身份、revision 与 AT 作为同一快照交付。
- 新会话切换复用 managed deployment/session 机制。目标预检核对来源、主体、工作区、授权、人工调度状态、分组、模型、能力和现有 scheduler 策略；使用 route revision CAS。
- 切换需要操作员显式输入模型、至少一种能力和 schedule_new_sessions=true；缺上下文时只返回安全状态与不可用原因。失败不写路由；重复选择当前 provider 为通过 CAS/预检后的幂等 no-op。
- 旧 session、在途请求、response、file 等资源保持 immutable binding；双份授权保留，目标缺授权时先授权。
- 旧 toSub2 受管账号不自动接管，不共享 RT。交接必须有显式围栏、确认无在途刷新、受保护传递、撤销旧发布权和持久回执；无法证明时保留旧模式或重新授权。
- API 字段、错误码、状态机和切换预检以同目录的 API 合同为准。六阶段采用 A → B，A/B → C，B → D，B/D → E，A–E → F 的已批准依赖。

## Testing Decisions

- 从公开 API 和模块可观察行为进行 RED → GREEN，复用既有 fixture、PostgreSQL/Redis 和 managed deployment/session 接缝；测试不放宽生产 origin、PKCE、state 或身份校验。
- 最高层验收入口是 Sub6 管理员登录/授权管理 → 核心 profile → gateway → 受控本地 BPS → 官方 Python/JavaScript SDK 的同一 Sub6 入口。
- 覆盖 JSON/SSE、工具往返、身份/资源隔离、重启、双向往返切换、旧会话绑定、人工停调和并发/迟到 401；toSub2 完全停机仍走核心路径。
- 刷新验证覆盖多实例 CAS、旋转持久化顺序、存储失败、结果未知、invalid_grant、错误来源过滤和重复失败 revision。
- 交接验证覆盖无明确所有权、旧刷新未退出、旧发布权未撤销、回执失败及重启恢复的闭锁分支。
- 合成 fixture 和受控 BPS 只证明相应测试边界；真实官方 OAuth、RT 轮换、BPS 模型/文件理解和计费分别需要真实证据。缺少用户官方授权时保留 blocked/待验，不关闭整项 Issue。
- 最终集成版本执行 Spec 与 Standards 两轴独立审查，保留失败、跳过和未验证项，修改后重验受影响范围。

## Out of Scope

- 本轮不推送、不创建 PR、不部署、不启用真实号池，也不隐式迁移真实凭据。
- 不读取真实 .env、auth.json、浏览器 storage 或其他秘密；真实官方登录由用户完成，不接收密码或验证码。
- 不替换原有普通 Codex 路径，不将 toSub2 设为核心依赖，不扩大 worker 的刷新所有权。
- 不重置、覆盖、整仓暂存已有 dirty；产品实现由对应所有者完成，本目录只记录已批准规格、任务和证据边界。
